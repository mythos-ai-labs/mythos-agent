# 建设路线、验证与评审

[返回导航](README.md) · 需求编号：[产品](01-product.md) · 技术决策：[选型](05-technology.md)

## 1. 决策状态与验证边界

**用户已确定**：本轮完成概念设计与选型论证，后续才进入详细设计和实现；本地 Web、通用 Harness、小说预置应用和作者控制是共同方向。

**设计建议**：先用通用任务验证可靠运行，再让小说场景证明领域建模价值。每一阶段以可观察成果验收，不以 Agent 数量、生成字数或框架部署数量衡量进度。

**待验证假设**：见本文件的试验清单。下述软件验收用例、性能目标与模型评估均为未来工作，当前没有可运行程序，不能宣称测试通过。设计桌面推演仅证明文档逻辑能够描述预期处理。

## 3. 详细设计前必须解决的试验

| 编号 | 待验证假设 | 最小试验与记录 | 失败后的处理 |
| --- | --- | --- | --- |
| EXP-01 | 自有 Harness 可以可靠接续 | 模拟模型与工具；在意图落盘前后、工具成功后、结果落盘后分别杀进程，核查恢复 | 收缩自动重试范围；复评编排框架，但仍保留应用事务 |
| EXP-02 | 多供应商具备可用公共能力 | 至少两个不同供应商跑相同的流式、工具、结构化输出、失败、取消和用量案例 | 按职责限制不兼容模型，必要时增加原生 SDK 适配器 |
| EXP-03 | SQLite 与驱动适合 Windows 分发 | 在干净 Windows 环境验证安装、中文路径、事务、备份、重启和 FTS5 能力 | 比较替代驱动或分发方式；不以开发机成功代替安装验收 |
| EXP-04 | 中文检索基线足够 | 构造短名、别名、人物知识、过期版本、模糊问题与长文样本；记录召回、延迟 | 改进实体别名、分词或子串策略，再评估向量增益 |
| EXP-05 | 编辑器可承载正文与提案 | 中文输入法、长文、选区改写、人工与模型并发修改、撤销重载和导出往返 | 简化编辑器功能或替换编辑核心；稳定版本语义不变 |
| EXP-06 | 审阅负担可接受 | 邀请目标作者完成一次确认、一次拒绝、一次修改事实；观察误操作与用时 | 调整分组、解释与默认展示；不以自动批准掩盖负担 |
| EXP-07 | Canon 与正文可一致提交 | 在事务、重复批准、过期基础版本、派生更新失败各点注入故障 | 先修复提交边界再继续领域功能 |
| EXP-08 | 凭据与本地访问边界可用 | 验证密钥不进入导出/日志、跨源调用受限、越界路径与 junction 被正确处理 | 不开放相关工具；凭据退回仅会话输入 |

试验记录包含日期、操作系统与硬件、依赖/模型版本、输入样例、结果、已知限制和决策影响。调用真实模型前使用明确的测试预算与非敏感样例；单元测试优先使用固定模型响应。

## 4. 两条端到端验收旅程

### 4.1 小说旅程

固定使用 [领域样例](02-domain.md) 中的《觉醒之前》。从 V12 开始：顾清持有地图；林烬和顾清都不知道哥哥主动消失的原因；本场景不可揭露具体身份。

1. 选择场景目标，系统展示所用时点、视角、规则及 Anchor。
2. 生成计划与草稿，提取地图转移、临时合作和怀疑隐瞒的候选变化。
3. 故意加入“顾清知道林烬的具体身份”的错误，检查系统能定位证据不足与揭露越界。
4. 作者改正后批准，正式正文与对应 Canon 同时进入 V13。
5. 在 V13 后提出“只展示地图”的修改，检查后文持图描写被列入待复核，不自动重写后文。
6. 导出正文并备份作品，在新的工作空间恢复；核对正文、Canon、提案、版本与附件。

小说验收包含文学评审，但模型自动评分不能代替作者决定。测试种子、规则和人物应完整固定，避免每次运行换故事导致难以对比。

### 4.2 通用资料旅程

导入三份旅行笔记，配置“资料助手”，授权范围只含这三份文件。要求输出地点清单、每条来源和冲突信息，不浏览外网、不改源文件。

中途断开浏览器，再重连；之后在受控步骤模拟服务退出并恢复。最终审阅并确认一份汇总产物，打开运行回放确认没有额外工具执行。该旅程不创建任何小说领域对象，也不依赖 Canon 校验器；若必须加载小说代码才能运行，则平台分层验收失败。

## 6. 设计桌面推演记录

以下记录为 2026-09-28 对文档方案的逻辑走查，未运行模型或产品程序。

| 推演 | 从文档得到的处理路径 | 仍需验证 |
| --- | --- | --- |
| 模型输出后网络失败 | 不完整草稿保留 → 当前步骤失败 → 新尝试重试 → 原作品不变 | SDK 的取消、计费和片段保存行为 |
| 导出成功后服务崩溃 | 意图存在、结果未知 → 核实目标文件 → 确认已完成或等待用户处理 | 实际执行器的去重与核实能力 |
| 提案被拒绝 | 生成运行可为已完成 → 提案为已拒绝 → V12 保持 → 回放可看候选 | 存储约束与界面文案一致性 |
| 旧提案在手工改稿后被批准 | 草稿/作品版本核验 → 发现基础过期 → 重算差异 → 重新校验与确认 | 并发边界与事务隔离 |
| 顾清过早得知身份 | Writer 上下文限制 → Critic 对照 Anchor 和正文证据 → 作者修正文或显式修订约束 | 语义检测的漏报率 |
| 世界时间与正文顺序不一致 | 选世界时点重建事实 → 按正文位置计算读者已知 → 组织视角上下文 | 历史状态查询正确性 |
| 通用资料任务接续 | 共享 Harness、产物和提案 → 无小说实体 → 通用审阅 | 包依赖检查和真实端到端运行 |

这些路径在概念层未发现必须由模型直接写入 Canon 或直接覆盖作品的缺口。它们不证明实现已具备防错能力。

## 7. 质量评估方法

| 维度 | 指标与样本 | 使用方式 |
| --- | --- | --- |
| 事务正确性 | 固定故障集内零次重复正式提交、零次正文/Canon 半提交 | 作为实现放行门槛；不推广成所有外部工具的恰好一次保证 |
| 信息边界 | 已标注的越权访问、跨空间污染、提前揭露样例 | 确定性权限违规零容忍；模型语义漏报单列并人工复核 |
| 状态抽取 | 按物品、关系、知识、故事线等标注精确率和召回率 | 区分错误事实与漏事实，不能只看总体准确率 |
| 检索 | 至少 30 条人工标注问题，含短名、别名与版本陷阱 | 初始探索目标为 Top-5 证据召回率 ≥90%；评审后再确定正式阈值 |
| 文学质量 | 动机可信、因果清楚、代价有效、状态有变化、文风适配 | 作者按维度评价并说明理由；模型评语仅辅助 |
| 编辑体验 | 完成确认/拒绝/修订的用时与误操作；中文输入丢字/覆盖情况 | 数据安全错误阻止发布；效率与美感用试用比较 |
| 长任务成本 | 每场景请求数、用量、重试率、作者修改时间 | 比较“只续写”与受控流程的收益，不以输出更长判胜 |
| 本地性能 | 固定硬件和 [产品负载样本](01-product.md)，分别测编辑、检索、提交、首事件延迟 | 不把供应商响应时延算作本地 UI 性能，不提前宣称 SLA |

每次模型或核心提示变更重跑固定样例，并增加本次发现的真实失败样例。人工与模型评估结论冲突时保留分歧，不静默调整指标以制造通过。
