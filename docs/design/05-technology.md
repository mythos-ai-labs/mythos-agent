# 技术选型与 Harness 对标

[返回导航](README.md) · 架构约束：[系统架构](04-architecture.md) · 试验安排：[路线与验证](07-roadmap-validation.md)

## 1. 决策状态与选型标准

**用户已确定**：TypeScript 优先、自有 Harness、复用成熟 SDK、多供应商自带密钥、本地 Web；不以封装某个既有 Harness 作为主路线。

**设计建议**：以 React + Vite、Node.js + Fastify、SQLite + Drizzle、AI SDK 组成基础栈；UI 使用可维护的组件代码，编辑器采用 Tiptap 开源核心；先把可恢复任务与内容版本机制做好。

**待验证假设**：自建执行循环的长期维护成本可接受；各供应商能通过统一的核心能力测试；Windows 安装、中文检索和编辑器性能达到产品目标。本文给出推荐而非锁定依赖版本，不代表已经安装或实测。

评估优先级依次为：领域与版本边界可控、可恢复和可测试、本地 Windows 可运行、多供应商接入、开发维护成本、后续扩展。框架功能数量不是主要指标。所有外部能力描述均基于 2026-09-28 核查的官方资料，选型结论属于本项目推断。

## 2. 产品与 Harness 对标

对标对象是公开可核查的代表方案，不声称覆盖全部市场或做过性能排名。

| 对象 | 已核查能力 | Mythos 借鉴什么 | 不直接作为主底座的原因 |
| --- | --- | --- | --- |
| OpenCode | 本地服务与客户端分离，公开会话、事件等接口；具有工具权限规则 | 会话与运行可观察性、统一权限入口、产物差异审阅 | 其能力围绕编码工作流组织；本项目希望直接掌握领域提交和运行契约 |
| Claude Agent SDK | 提供 Claude Code 的循环、工具、会话、权限与扩展能力，支持 TypeScript | 成熟 Harness 的职责覆盖、长任务上下文、工具生命周期 | 主路线要求多供应商及自有运行机制；直接嵌入会承担底座语义和供应商耦合 |
| Anthropic 长任务实践 | 强调可接续进度、任务分解与跨会话交接材料 | 用任务清单、检查点和产物支撑接续 | 编码实验经验不能直接证明小说质量或本平台恢复可靠性 |

来源：[OpenCode 服务](https://opencode.ai/docs/server/)、[权限](https://opencode.ai/docs/permissions/)、[Claude Agent SDK 概览](https://code.claude.com/docs/en/agent-sdk/overview)、[长期任务 Harness 经验](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。核查：2026-09-28。

若未来提供这些底座的适配入口，应作为显式选择的执行器，并说明哪些任务状态、审批和恢复能力无法与自有 Harness 等价。当前不规划双套运行机制同时落地。

## 3. 自有循环、AI SDK 与 LangGraph 的取舍

| 路线 | 获得的能力 | 仍需自己承担 | 结论与变更条件 |
| --- | --- | --- | --- |
| 自有 Harness + AI SDK | 多供应商接入、流式输出、工具定义与模型返回处理 | 持久任务、权限、恢复、提交一致性、上下文策略、预算 | 推荐；所有执行仍经过平台调度与权限入口 |
| LangGraph JS 编排 + 模型适配 | 图式执行、检查点与存储等编排能力 | 领域版本、外部副作用去重、权限、应用 UI、部署和数据库适配 | 备选；分支、子任务及恢复复杂度明显超过自有循环维护能力时复评 |
| 直接使用各供应商 SDK | 更直接访问供应商特有能力 | 重复适配、消息差异、流处理、错误分类及全部 Harness | 作为特殊能力的适配器后备，不让业务层直接调用 |

AI SDK 官方列出专用 provider 和自定义 provider 接入方式；工具执行函数是可选的，因此可以把执行交给自己的调度器。它也提供工具审批相关机制，但这不自动等于本地服务重启后仍可恢复审批。[供应商选择](https://ai-sdk.dev/docs/getting-started/choosing-a-provider)、[工具调用](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling)，核查：2026-09-28。

建议显式实例化选定供应商并使用其密钥，不依赖隐式模型路由或默认网关；任何新增数据接收方都需体现在用户配置与上下文发送说明中。SDK 内建循环若被使用，只能作为单个受控步骤的实现，不能在平台预算、权限和持久化之外继续执行工具。

LangGraph 区分按会话保存图状态的 checkpointer 与跨会话 store，内存存储不能跨进程重启恢复。这些能力值得参考，但图检查点不能代替正文与 Canon 的原子提交。[LangGraph 持久化](https://docs.langchain.com/oss/javascript/langgraph/persistence)，核查：2026-09-28。

## 4. 技术选型矩阵

以下各项都是设计建议。“替代方案”表示重新评审的方向，不承诺替代项已做同等深度的测试。

| 层面 | 推荐基线 | 主要理由与代价 | 替代方案及更换条件 |
| --- | --- | --- | --- |
| 语言与运行时 | TypeScript strict、受支持的 Node.js LTS | 统一核心契约与前后端语言；静态类型不替代运行时校验 | Bun 等运行时仅在 Windows、数据库驱动和工具兼容试验通过后考虑 |
| 前端 | React + Vite | 适合本地交互工作台；当前没有公共页面 SEO/SSR 需求 | Next.js：出现明确的服务端页面需求时；Vue：团队维护优势改变时 |
| 本地服务 | Fastify | 本地长驻进程和接口边界清晰；具备 TypeScript 支持 | Hono 或其他 HTTP 层：部署约束变化时；不改变 Harness 所有权 |
| UI | shadcn/ui 组件代码 + Tailwind CSS + 自有设计变量 | 可定制双工作台及审阅面板；团队承担复制后的组件维护 | 成套组件库：复杂表格及表单占据主导且定制负担过大时 |
| 编辑器 | Tiptap 开源核心及必要扩展 | 支持自定义富文本体验；需要自己做业务版本、差异与批注关联 | Lexical 或以 CodeMirror 为基础的纯文本编辑：长文/中文输入试验失败或转向纯 Markdown 时 |
| 持久存储 | 每空间 SQLite + Drizzle | 降低服务部署成本，显式管理事务和迁移 | PostgreSQL：出现多用户、远程共享写入或实际并发瓶颈时 |
| SQLite 驱动 | 先验证 better-sqlite3 | 通过 Drizzle 接入；原生依赖的 Windows 分发需验证 | node:sqlite：目标 Node 能力、稳定性和驱动测试通过后再比较 |
| 运行时校验 | Zod，边界契约可映射 JSON Schema | 为用户输入、模型输出、工具参数建立统一校验 | 原生 JSON Schema 校验器：协议兼容需求超过 Zod 映射能力时 |
| Agent 执行 | 自有显式循环、持久检查点与审批记录 | 直接控制行为和提交边界；需要严格的恢复试验 | LangGraph JS：见上一节的复杂度触发条件 |
| 模型接入 | AI SDK 的显式 provider 适配 | 复用流、调用与错误转换；厂商能力仍需逐项测试 | 特定供应商原生 SDK 适配器：关键能力缺失或适配滞后时 |
| 事件通信 | HTTP 命令/查询 + SSE 进度 | 符合当前服务向页面推送的需求 | WebSocket：实时协作或持续双向低延迟输入出现时 |
| 检索 | 关系查询、实体别名、SQLite FTS5 | 本地可部署，可先用明确来源验证检索质量 | 分词扩展/向量检索：基准证明有净增益后引入 |
| 关系与时间线 | 关系表表达节点和边，应用层投影 | 先验证领域关系本身，避免先承担图数据库运维 | 图数据库：深层遍历成为经测量的瓶颈时再选型 |
| 扩展接入 | 内置注册机制，后续接入 MCP | 控制扩展范围，再复用协议生态 | 不定义私有协议去替代 MCP；非兼容工具通过显式适配器接入 |
| 测试 | Vitest + Playwright | 分别验证状态逻辑和浏览器用户旅程 | 真实模型评估独立于常规测试，避免把网络波动当代码回归 |
| 可观测性 | 本地结构化日志与运行事件；保留 OpenTelemetry 接口 | 首期可诊断、可脱敏，不强制外部服务 | 多进程追踪需求增加时启用 OTel；云端导出由用户显式配置 |

矩阵能力依据均为官方资料，核查日期 2026-09-28：[React](https://react.dev/learn)、[Vite](https://vite.dev/guide/)、[Fastify TypeScript](https://fastify.dev/docs/latest/Reference/TypeScript/)、[shadcn/ui](https://ui.shadcn.com/docs)、[Tiptap](https://tiptap.dev/docs/editor/getting-started/overview)、[Drizzle SQLite](https://orm.drizzle.team/docs/sqlite/get-started-sqlite)、[Zod](https://zod.dev/)、[Vitest](https://vitest.dev/guide/)、[Playwright](https://playwright.dev/docs/intro)、[OpenTelemetry JavaScript](https://opentelemetry.io/docs/languages/js/)。

Tiptap 开源核心与其商业/云端扩展的能力边界不同。上述推荐不包含购买其云端版本历史、协作或 AI 服务，Mythos 的正式作品版本和变更提案由本地应用负责。实施时对实际使用的扩展逐项核对许可和费用。[Tiptap 官方概览](https://tiptap.dev/docs/editor/getting-started/overview)，核查：2026-09-28。

## 5. 中文检索与 RAG 决策

RAG 在这里表示“按任务检索可引用的证据，再组织上下文”，并不以向量数据库为前提。先按工作空间、版本、时点、视角和权限过滤；人物、地点、物品及其别名优先使用结构化精确查询，正文再用全文或子串检索。

FTS5 的默认 unicode61 以连续 token 字符分组，不能直接等同于中文语义分词。trigram 适合子串候选召回，但全文查询中少于三个 Unicode 字符的片段存在明确限制。因此“林烬”“顾清”等二字姓名必须通过实体别名和受限子串检索补充，不能只靠 trigram。[SQLite FTS5 tokenizer 说明](https://www.sqlite.org/fts5.html)，核查：2026-09-28。

以精确事实查询、模糊意图查询、短姓名、别名、旧版本和剧透过滤构造基准。只有在全文基线不足且嵌入检索提高召回而不破坏权限/时序过滤时，才增加向量索引；向量结果仍需返回源片段和版本。嵌入供应商会新增数据发送与成本，应单独配置。

## 6. 模型能力与版本管理

为每个实际启用的模型验证：流式文本、工具调用、结构化结果、上下文预算、取消、错误分类、用量返回及中文叙事表现。兼容某种 API 外形不代表工具语义、严格结构约束和计费信息等价。

不支持工具调用的模型只能用于适合纯文本的职责；不能在 UI 中允许它承担需要执行工具的工作流而默默降级。Planner、Writer、Critic 可以有不同模型配置，但首轮用最少配置验证闭环，复杂路由后置。

实施开始时选择满足要求的稳定发布组合，提交锁文件和兼容性记录。官方文档的 latest 页面、示例中的预发布安装指令均不自动成为依赖策略；不能从“官方页出现某驱动”推断该版本已满足项目的 Windows 安装要求。

## 7. 关键风险、成本与验证门槛

| 风险 | 限制影响的设计 | 验证与失败后处理 |
| --- | --- | --- |
| 自有恢复逻辑遗漏边界 | 把检查点、工具意图、外部结果及业务提交分开 | 杀进程注入；失败则收缩自动恢复范围或复评编排框架 |
| 模型能调用但输出质量不稳 | 统一能力矩阵、结构校验、作者审阅 | 两家供应商同一套样例；不通过的职责不开放 |
| 中文检索漏掉短名或旧设定 | 实体查询和版本过滤优先 | 基准未达标先改分词与检索，不能靠扩大提示掩盖 |
| 富文本依赖难以版本化 | 规范正文模型与稳定引用，候选内容隔离 | 中文输入、撤销、重载、Markdown 往返试验；失败则简化编辑能力 |
| 原生依赖影响 Windows 安装 | 驱动单独适配，固定支持矩阵 | 干净 Windows 环境试装；失败再比较内置驱动或分发方案 |
| 成本随 Critic/重试膨胀 | 任务预算、限制无进展循环、复用确定性检查 | 记录每场景请求和人工修订成本，按实际质量增益减少调用 |
| 本地凭据方案不跨平台 | 凭据接口隔离、无安全存储时仅会话输入 | Windows 优先验证，再扩展 macOS/Linux |

暂不引入独立消息队列、分布式工作流服务、图数据库和专用向量服务。它们的引入条件是当前方案的可复现限制，而不是因为项目名称包含 Agent。所有技术试验必须记录版本、环境、输入和结果；本轮只完成资料核查与论证。
